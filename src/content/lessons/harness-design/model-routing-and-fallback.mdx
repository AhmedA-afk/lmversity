A harness that only ever talks to one model, one endpoint, is one outage away from being useless. Model routing decides *which* model handles a given call; fallback decides what happens when that model can't.

## Routing by task, not by default

Most harnesses are built around a single "the model" assumption, but a real control loop touches several kinds of work in one session: a cheap classification, a long tool-heavy plan, a quick summarization pass. Routing means picking the model for each call based on what the call actually needs — not hardcoding one model for everything.

A simple router is just a lookup keyed on call type:

```
route("intent-classify")   -> small, fast model
route("plan-and-act")      -> frontier model, extended thinking on
route("summarize-tool-output") -> small model, no thinking
```

The signal for routing can be static (the harness always sends subagent grunt work to a cheaper model) or dynamic (a difficulty estimate, a token-budget check, or the previous call's confidence decides). Static routing is easier to reason about and debug; dynamic routing saves more money but adds a failure mode of its own — a misrouted "easy" call that was actually hard, silently producing a worse answer with no error to catch.

The trap to avoid is routing on model name instead of on capability. Hardcode `"claude-opus-4-5"` into your router and the day that model is deprecated, every call site breaks at once. Route on a capability label your harness owns — `"reasoning-tier"`, `"fast-tier"` — and keep the label-to-model mapping in one place, so a model swap is a one-line config change instead of a grep-and-replace across the codebase.

## Fallback is routing under failure

Fallback is the same mechanism triggered by an error instead of a task type: the primary model call errors, rate-limits, or times out, and the harness needs a decision about what to try next, rather than surfacing a raw exception to the user mid-agent-loop.

The three fallback strategies you'll actually use:

<Compare title="Fallback is routing under failure">
<Pane title="Retry the same model" tone="good">
Transient errors — 5xx, connection resets — with exponential backoff. Usually correct first: it doesn't change behavior.
</Pane>
<Pane title="Fail over to another provider" tone="neutral">
Sustained outage or a rate-limit backoff won't clear. The fallback target uses the same capability-tier logic as normal routing.
</Pane>
<Pane title="Degrade the request" tone="neutral">
Drop to a smaller model or smaller context — for 'too expensive or too slow right now,' not 'provider is down.'
</Pane>
</Compare>

The dangerous failure mode is silent degradation with no signal. If a harness quietly falls back from a frontier model to a much weaker one on every timeout, a user watching consistent-looking output has no way to know quality just dropped. Log every fallback event — which tier, why, what triggered it — the same way you'd log a [retry](/learn/harness-design/harness-observability). Treat model choice as part of the trace, not an implementation detail buried inside the call.

Fallback also needs a circuit breaker, not just a retry loop. A provider that's down doesn't need five retries per request across a thousand concurrent calls — it needs the harness to notice after the first few failures and stop sending traffic there until a health check says it's back.
