If a human isn't staring at a spinner waiting for the response, you're probably paying too much for it. Batch APIs trade latency for cost: submit a pile of requests, get results back in hours instead of milliseconds, and pay roughly half the per-token price.

## What actually counts as "batch work"

Not every job needs a synchronous round trip. Nightly re-scoring of support tickets, bulk-classifying a backlog of documents, generating embeddings for a new corpus, re-running evals across a prompt change, backfilling summaries for old records — none of these have a user refreshing a page waiting on them. The defining trait isn't volume, it's whether a delay of minutes to a day is acceptable. If yes, it belongs in a batch queue, not your normal request path.

Anthropic's Message Batches API and OpenAI's Batch API both work the same way: you upload a file of requests (each with its own `custom_id`), the provider processes them asynchronously against spare capacity, and you poll or get notified when the batch completes — typically within 24 hours, often much faster. In exchange, both charge about 50% less than the interactive endpoint for the same tokens. That discount is the entire reason this pattern exists.

## Building the pipeline

The mechanics are simple but the plumbing matters more than the API call itself:

<Steps>
<Step title="Collect requests">
Write a JSONL file — one line per request, each tagged with its own `custom_id` so you can map results back later.
</Step>
<Step title="Submit the batch">
Upload the file and get back a `batch_id`. This is a handoff, not a function call.
</Step>
<Step title="Wait for completion">
Poll the batch status, or use a webhook if the provider supports one. Batches aren't guaranteed to finish in order, or even all at once.
</Step>
<Step title="Map results back">
Download the results file and join each line to your records via `custom_id`.
</Step>
<Step title="Handle partial failures">
Individual requests inside a batch can fail while the rest succeed — expect a results file that mixes successes and errors, not uniform output.
</Step>
</Steps>

<Callout kind="breaks" title="Where batches bite">
- **Treating it like a blocking call.** A batch is fire-and-forget with a callback, not something you `await`. Code that assumes in-order, all-at-once completion will mishandle real batches.
- **Assuming uniform results.** Your ingestion path must tolerate a mix of successes and per-line errors in the same file — the batch succeeding says nothing about any single request inside it.
</Callout>

## Where it fits next to caching and routing

Batch APIs solve a different problem than [prompt caching](/learn/production/prompt-and-semantic-caching) or [model routing](/learn/production/model-routing-by-task-complexity). Caching cuts cost when you repeat the *same* context across calls; routing cuts cost by sending easy requests to a cheaper model. Batching cuts cost by relaxing the *time* constraint — same model, same prompt, just no rush. They stack: a nightly reclassification job can run on a cheap model, through the batch endpoint, with a cached system prompt, for a fraction of what the naive interactive-API version would cost.

The main mistake teams make is defaulting everything to interactive calls because it's the path they already built, then wondering why the bill is high. Any workload where "results by tomorrow morning" is fine is money left on the table if it's still hitting the synchronous endpoint.
