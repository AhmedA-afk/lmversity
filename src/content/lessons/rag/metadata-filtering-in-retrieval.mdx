Vector similarity alone doesn't know that a user shouldn't see another team's documents, or that a query about "this quarter's numbers" should exclude last year's report. Metadata filtering fixes that by narrowing the candidate set with structured fields before or alongside the similarity search.

## Why similarity search isn't enough

An embedding captures meaning, not access control or recency. If you ask "what's our refund policy" and the vector index only ranks by cosine distance, it might just as happily return a draft policy from two years ago, or a document from a customer you don't have permission to view, as long as the wording is close enough. The fix isn't a better embedding — it's attaching metadata (owner, department, date, document type, permission tags) to every chunk at ingestion time, then filtering on it at query time.

## Pre-filter vs. post-filter

There are two places to apply the filter, and the difference matters:

- **Pre-filtering** restricts the candidate pool to matching metadata *before* running the similarity search. This is the safer default for permissions — if a user can't see a document, it should never enter the ranked list at all.
- **Post-filtering** runs the vector search first, then drops results that fail the metadata check afterward. It's simpler to bolt on, but it's risky: if your top-k similarity search returns 10 results and 8 get filtered out, you may end up with too few (or zero) usable results, even though better matches existed further down the ranked list.

Most production systems lean toward pre-filtering, or a hybrid where the filter is pushed into the same query the vector database executes, so the index only searches within the allowed subset. See [Choosing a Vector Database](/learn/rag/choosing-a-vector-database) for how well different databases support this natively — it varies a lot, and it's one of the more consequential choices you'll make.

## Designing filterable metadata

Good metadata fields are decided at ingestion, not bolted on later, so plan them alongside your [chunking strategy](/learn/rag/chunking-strategies-for-documents):

- **Access control**: user ID, team, role, or a permissions list per chunk.
- **Time**: publish date, last-updated date, or a validity window — critical for anything that goes stale.
- **Category**: document type, product line, language, source system.

Keep filter fields separate from the text you embed. Don't try to smuggle "only search HR docs" into the query text and hope the embedding model figures it out — it won't reliably. Express it as a structured filter (a `WHERE`-like clause most vector databases support) instead.

<Callout kind="breaks" title="Permissions in the query text is a hope, not a filter">
"Only search HR docs" written into the embedded query is a suggestion the embedding model may or may not honor — similarity doesn't understand access control. Scope is a structured `WHERE`-style clause, executed by the index, every time.
</Callout>

## Combining with hybrid search

Metadata filtering composes cleanly with [hybrid search](/learn/rag/hybrid-search-lexical-and-vector): the metadata filter narrows *which* documents are eligible, while the lexical and vector components decide *which of those* are most relevant. Think of metadata as answering "is this document even in scope," and similarity as answering "how well does it match the meaning of the query." Getting the first question wrong is a correctness and security bug; getting the second wrong is just a quality problem.
