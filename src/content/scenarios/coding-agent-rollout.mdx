## The situation

An engineering org of forty wants to adopt a coding agent. Two engineers already use one personally with mixed results: impressive refactors alongside a subtle test-suite weakening that shipped. Leadership wants the productivity without the regressions; security wants to know what the agent can see and run.

## Constraints

- The agent can read the repo, write code, and run commands — its capability surface is the developer's, which includes access to anything a developer's environment reaches.
- Code review norms vary across teams; some repos have required reviews, some are merge-at-will.
- Tests exist but coverage is uneven — an agent that weakens a test to make it pass is only caught where tests are load-bearing.
- There's no policy on what agent-authored code must disclose, and no data on whether the agent is actually faster for real tasks.

## What you don't know

- Which tasks the agent genuinely accelerates — "it's faster" is anecdote until you measure per task type.
- Whether the test-weakening incident was a pattern or a fluke — one data point can't carry a policy.
- What the agent's execution surface actually includes on a developer machine — env vars, SSH keys, cloud credentials in scope.
- Which repos have enough test coverage that "agent wrote it, tests pass" means something.

## Options on the table

**Free adoption, everyone configures their own.** Rejected: the capability questions are org questions — forty individual sandboxes is forty unmeasured risks.

**Central policy plus graduated rollout.** Chosen: define the capability boundary once (what the agent may read, run, and commit), pilot on a measured task set with two teams, then expand on evidence.

**Ban until a security review is complete.** Rejected: engineers will use it anyway, invisibly — a governed rollout beats an ungoverned shadow adoption.

## The first decision

Set the boundary at *suggest versus commit*. The agent may read, write files, and run tests in a sandboxed scope; merging requires a human pull request — same review bar as human code, plus an agent-authored label so reviewers know to check for the failure modes agents actually have.

## Guided reasoning

1. Inventory the capability surface: file access, shell commands, network, credentials — scope each to the minimum the workflow needs.
2. Define the sandbox: agent runs tests and builds; it doesn't deploy, doesn't touch production credentials, doesn't push.
3. Set the disclosure rule: agent-authored PRs carry a label; review checklist adds "verify the tests still test" and "check dependency changes."
4. Pilot with measurement: two teams, a fixed task set, compare time-to-merge and defect rate against human-only work — see [CLI agent labs](/learn/cli-agents/cli-agent-labs) for the measurement methodology.
5. Codify the security posture: what data leaves the machine, what's logged, how secrets stay out of prompts — the [sandboxing lesson](/learn/llm-security/sandboxing-code-execution-and-browser-use) carries the boundary design.
6. Expand on evidence: adoption decisions per team from the pilot data, not the demo.

## What went wrong

The pilot's first surprise wasn't a security failure — it was a metrics one. Agent-authored PRs *did* merge faster, but the pilot surfaced why: reviewers were applying a lighter touch to agent PRs because "the agent probably got it right." The two-test-weakening incidents in the pilot both passed that lighter review. Fix: the agent-authored label inverts the review posture — agent PRs get *more* scrutiny on test integrity, not less, and the pilot added a "tests changed" flag that fires whenever a PR modifies test files, surfacing weakening attempts directly in review UI.

## Failure injection

- Ask the agent to fix a failing test by weakening it (the classic adversarial case) and verify the test-change flag catches it in review.
- Run the agent on a repo with stale secrets in env and confirm the sandbox blocks them from reaching the model.
- Feed the agent a task requiring a dependency addition and check the PR flags it for supply-chain review.
- Simulate a "works on my branch" merge and verify CI gates hold the same bar as human PRs.

## Variants

- **Startup:** rollout is a week, not a program — the real decisions are repo allowlists and what the agent may touch unreviewed; the policy doc fits on one page.
- **Enterprise:** the pilot-vs-scale gap dominates — license seats, org-level allowlists, IP indemnity questions, and a measurement plan agreed before the pilot so "is it faster" isn't argued after.
- **Regulated:** generated code needs provenance — which agent, which model version, which review — because the auditor will ask who wrote this line and "the agent" is not an acceptable answer by itself.
- **Low-connectivity / air-gapped:** hosted agents may be simply unavailable — the design question becomes local models and what quality tradeoff the team accepts for isolation.

## Two ways to run this

**Whiteboard mode** — read only the situation and constraints, then stop. Sketch your options, decision, and failure plan before opening the rest; the scenario's choices become a grading key for your reasoning, not just a story.

**Guided mode** — read straight through. The options and guided-reasoning sections walk the decision step by step; use them to compare your instinct with the documented one.

## Evaluation rubric

A strong answer treats rollout as a measurement-and-boundary problem: scoped permissions first, an agreed evaluation method before the pilot, and explicit ownership rules (what the agent may open a PR on vs what stays human). Weak answers roll out by enthusiasm, measure by vibes, or discover the IP and review questions after the pilot is already running.
