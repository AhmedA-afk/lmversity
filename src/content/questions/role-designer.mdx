## What the role interview tests

Designer interviews for AI products test whether you can design for systems that are *probabilistic*: outputs that vary, capabilities that surprise in both directions, and failure modes that are part of the experience rather than edge cases. The craft bar is the same as ever — the new dimension is trust calibration and designing the wrong answer well.

**Core topic hubs:** [AI foundations](/interview/ai-foundations) · [Behavioral and project defense](/interview/behavioral-and-project-defense) · [LLM basics](/interview/llm-basics) · [Safety and security](/interview/safety-and-security) · [Evals](/interview/evals)

## Mock set — junior

1. AI foundations Q1–Q4 (what these systems do and don't)
2. LLM basics Q1–Q2 (plain-language mechanics — enough to design against)
3. Behavioral — how you handled an ambiguous brief
4. A critique question: what's wrong with this AI feature's UX
5. Defend-project on any shipped design

*Pass bar:* accurate mental models, no magic-thinking, designs for the user not the demo.

## Mock set — mid

1. Design-this-system: the failure and empty states of an AI feature (often the real test)
2. Choose-tradeoff: confidence display — when to show uncertainty and how
3. Behavioral — a disagreement with engineering about what was possible
4. Safety — what injection/misuse means for an interface you design
5. Critique: an AI flow that over-promises

*Pass bar:* treats loading, partial, wrong, and refused states as first-class design surface; knows uncertainty can be designed, not hidden.

## Mock set — senior

1. Design-this-system: an AI feature end to end — onboarding through failure recovery
2. Choose-tradeoff: automation that saves time vs agency that preserves control
3. Behavioral — a design that handled AI failure well or badly; what changed
4. Critique: a trust-caliper problem — an interface that makes users over-trust
5. Defend-project on your most consequential AI design decision

*Pass bar:* argues about user trust as a design material; knows the difference between a capability demo and a trustworthy feature.

## What interviewers probe for this role

- **The wrong answer is a design surface.** Deterministic software hides failure; AI features produce plausible-wrong output as a normal event. Strong candidates design for it explicitly.
- **Trust calibration.** Over-trust is the safety-relevant failure; under-trust is the adoption failure. The interface sets the dial.
- **Capability realism.** Knowing what models can and can't do — enough to push back on a spec that assumes magic, and to spot where the spec under-uses the capability.

## Project defense

Expect: which states you designed (and which you didn't — be honest), how the interface handles a wrong-but-confident output, what user research told you about trust, and the decision you'd revisit. The [designer capstone](/learn/ai-for-designers/capstone-design-a-trustworthy-ai-feature) is built as exactly this defense material.
